# Controlplane Schema Language (CSL)
## Specification — Draft v0.2

**Status:** Proposal  
**Purpose:** Declarative resource schema definition for Controlplane

---

## 1. Introduction

Controlplane Schema Language (CSL) is a declarative language for defining resource kinds, their fields, types, validation rules, defaults, and lifecycle state.

CSL is designed to support a dynamic resource system where resource kinds can be registered, modified, and versioned at runtime without requiring database migrations or application restarts.

CSL describes the structure and validity of resources. It does not define authorization, storage layout, API endpoints, reconciliation logic, or controller implementation.

The language deliberately avoids arbitrary executable code. Schemas should be declarative, predictable, portable, and straightforward to validate.

### Design principles

- Human-readable and concise syntax.
- Strong typing and explicit validation.
- Runtime registration of resource kinds.
- No database-specific schema requirements.
- Partial updates with complete post-update validation.
- Explicit schema versioning.
- No arbitrary code execution.
- Separation of schema and authorization policy.
- No mandatory metadata or identity structure.

## 2. Resource declarations

A resource kind is declared using the `resource` keyword, followed by its name and schema version.

```csl
resource VirtualMachine version 1 {
    name: hostname
    namespace: string

    desired {
        cpu: int16 range 1 to 128
        memory: bytes range 512MiB+
        image: string
    }

    observed {
        phase: string oneof(pending provisioning running stopped failed)
        ready: bool = false
    }
}
```

Resource names use PascalCase. Keywords, field names, and built-in types use lowercase.

A resource declaration contains:

- Resource-level fields.
- Optional `desired` section.
- Optional `observed` section.

A resource does not have to declare either section. It may consist entirely of resource-level fields.

### 2.1 Runtime identity

Every resource receives a runtime-generated, globally unique `uid`.

The `uid`:

- Is generated by Controlplane.
- Is immutable.
- Is used internally to identify a resource.
- Does not need to be declared in CSL.
- Cannot be supplied or changed by clients.

The runtime identity is independent of the resource schema.

Fields such as `name`, `namespace`, `tenant`, and `customer_id` are ordinary schema fields. CSL does not assign them special identity or uniqueness semantics.

A resource may define its own business identity using any combination of fields.

## 3. Resource sections

### 3.1 Resource-level fields

Fields declared directly inside a resource are ordinary resource fields.

```csl
resource Customer version 1 {
    customer_id: uuid
    tenant: string
    display_name: string
    labels: map[string]string optional
}
```

CSL does not require a particular set of resource-level fields.

For example, `name`, `namespace`, `labels`, and `annotations` are not mandatory.

### 3.2 Desired state

The `desired` section describes the state requested by a user, another system, or an authorized API client.

```csl
desired {
    cpu: int16 range 1 to 128
    memory: bytes range 512MiB+
    image: string
}
```

The desired state represents intent. Controllers can observe changes to it and reconcile the actual system toward that intent.

The runtime must preserve the distinction between desired state and observed state.

### 3.3 Observed state

The `observed` section describes the state reported by controllers or other authorized system components.

```csl
observed {
    phase: string oneof(pending provisioning running stopped failed)
    ready: bool = false
    ip_address: ip optional
    node: hostname optional
}
```

Observed state is not a declaration of user intent. It represents information about the actual resource or its reconciliation progress.

CSL does not prescribe how many controllers may update observed state.

### 3.4 Section semantics

`desired` and `observed` are reserved section names with lifecycle semantics.

They are not authorization declarations.

Authorization policy determines which identities may read or modify these sections. The runtime enforces those policies independently of CSL.

## 4. Field declarations

A field declaration has the following general form:

```csl
field_name: type [constraints] [optional] [= default]
```

Examples:

```csl
hostname: hostname
enabled: bool = true
description: string optional
port: uint16 range 1 to 65535
```

Field names must be unique within their containing object or section.

Unknown fields must be rejected unless a future language extension explicitly permits them.

Canonical representations should be used for serialization.

Recommended representations:

- `date`: ISO 8601 date.
- `time`: ISO 8601 time.

## 6. Numeric constraints

The `range` constraint defines an inclusive range unless otherwise specified.

```csl
cpu: int16 range 1 to 128
port: uint16 range 1 to 65535
temperature: float32 range -40 to 150
memory: bytes range 512MiB to 1TiB
```

For byte quantities, binary and decimal unit suffixes should be supported.

Recommended binary units:

- `KiB`
- `MiB`
- `GiB`
- `TiB`
- `PiB`

Recommended decimal units:

- `KB`
- `MB`
- `GB`
- `TB`
- `PB`

A trailing `+` represents an inclusive minimum with no explicit upper bound.

```csl
memory: bytes range 512MiB+
```

This is equivalent to a minimum of 512 MiB.

## 7. String constraints

String length constraints are expressed in characters.

```csl
name: string length 1 to 63
description: string length 0 to 1024
```

Implementations must define a consistent Unicode character-counting model.

## 8. Enumerations

The `oneof` expression restricts a value to a finite set of allowed values.

```csl
model: string oneof(q35 i440fx virt pc)
```

Commas between values are optional.

Quoted values are supported:

```csl
phase: string oneof("not started" "in progress" completed)
```

For string enumerations, unquoted identifiers represent literal string values.

An enumeration may also be defined as a reusable type in a future extension.

## 9. Lists and cardinality

List types use square brackets.

```csl
networks: ip[]
```

Cardinality constraints are expressed using a range inside the brackets.

```csl
networks: ip[1:8]
```

Supported forms:

| Syntax | Meaning |
|---|---|
| `string[]` | Zero or more elements |
| `string[8]` | Zero to eight elements |
| `string[1:8]` | One to eight elements |
| `string[5:5]` | Exactly five elements |
| `string[1:]` | At least one element |
| `string[:]` | Zero or more elements |

Nested lists are supported.

```csl
matrix: int16[1:8][1:8]
```

List constraints apply to the number of elements, not the serialized size.

## 10. Maps

Maps use Go-like generic syntax.

```csl
labels: map[string]string
```

The syntax is:

```csl
map[key_type]value_type
```

Examples:

```csl
labels: map[string]string
ports: map[string]uint16
addresses: map[string]ip
```

Map values may themselves be lists or maps.

```csl
networks: map[string]ip[1:8]
nested: map[string]map[string]string
```

Map keys must be scalar types with stable equality and serialization semantics.

## 11. Optional fields and defaults

Fields are required by default.

An optional field may be omitted.

```csl
description: string optional
```

A field may define a default value.

```csl
enabled: bool = true
model: string oneof(q35 i440fx virt pc) = q35
```

Defaults are applied when a resource is created and the field is omitted.

A defaulted field is present in the resulting resource.

An optional field without a default may remain absent.

Optionality and nullability are distinct concepts. In this version, `optional` means the field may be absent. Explicit `null` values are not permitted unless a future nullable type or modifier is introduced.

## 12. Objects and custom types

Named object types can be declared for reuse.

```csl
type ResourceLimits {
    cpu: int16 range 1 to 128
    memory: bytes range 512MiB+
}

resource VirtualMachine version 1 {
    desired {
        limits: ResourceLimits
    }
}
```

Nested object declarations are also supported.

```csl
resource Database version 1 {
    desired {
        storage {
            size: bytes range 1GiB+
            type: string oneof(ssd hdd)
        }
    }
}
```

Object fields follow the same required, optional, default, and validation rules as resource-level fields.

## 13. Conditional validation

Conditional validation allows fields to be required or constrained based on another field's value.

Proposed syntax:

```csl
resource Database version 1 {
    desired {
        backup_enabled: bool = false

        if desired.backup_enabled {
            backup_schedule: crontab
            backup_retention: uint16 range 1 to 365
        }
    }
}
```

When the condition is true, fields inside the block are required unless declared optional or given defaults.

When the condition is false, those fields are not required. If supplied, they must still satisfy their declared types and constraints.

Conditions must be declarative expressions. Arbitrary code and external function calls are not permitted.

The exact expression grammar is reserved for a later specification revision.

## 14. Resource updates and validation

CSL defines validation of complete resource state.

The runtime must support partial updates.

For example, an update containing only:

```text
desired.cpu = 4
```

must change only that field.

The update process is:

1. Load the current resource.
2. Apply the requested patch to the relevant fields.
3. Enforce authorization on the requested changes.
4. Validate the complete resulting resource against its schema.
5. Commit the update atomically.
6. Publish the resulting change event.

An update must not silently replace unspecified fields with defaults or zero values.

Explicit field removal must be distinguishable from omission.

Removing a required field must fail validation unless the update supplies a valid replacement.

The runtime must not permit a patch to bypass validation by modifying only a subset of fields.

## 15. Schema versioning

Every resource kind has an explicit schema version.

```csl
resource VirtualMachine version 1 {
    desired {
        cpu: int16 range 1 to 128
    }
}
```

Schema versions are immutable once registered and used to validate resources.

A changed schema must be registered as a new version.

```csl
resource VirtualMachine version 2 {
    desired {
        cpu: int16 range 1 to 256
    }
}
```

Migration between versions is a runtime concern and is not executable CSL functionality.

The control plane must retain the schema version associated with each resource so that historical resources and events can be interpreted correctly.

## 16. System-managed fields

The runtime maintains internal fields independently of CSL.

Recommended fields include:

| Field | Purpose |
|---|---|
| `uid` | Immutable resource identifier |
| `kind` | Resource kind |
| `schema_version` | Schema version |
| `resource_version` | Version of the stored resource |
| `generation` | Version of desired state |
| `created_at` | Creation timestamp |
| `updated_at` | Last modification timestamp |
| `deleted_at` | Deletion timestamp, when applicable |

These fields are not declared by resource authors and cannot be overwritten through ordinary resource updates.

`generation` increments when desired state changes.

`resource_version` changes whenever the stored resource changes.

## 17. Reserved words

The following identifiers are reserved in this version:

- `resource`
- `type`
- `desired`
- `observed`
- `if`
- `oneof`
- `optional`
- `range`
- `length`
- `map`
- `to`

Additional reserved words may be introduced in future versions.

## 18. Explicit non-goals

CSL does not define:

- Authentication.
- Authorization policies.
- Role or user assignments.
- Storage engines or database schemas.
- Event brokers.
- API routing.
- Controller implementation.
- Reconciliation scheduling.
- Arbitrary functions or scripts.
- Resource identity conventions such as mandatory `name` or `namespace`.

These concerns belong to other parts of Controlplane.

```csl
resource VirtualMachine version 1 {
    name: hostname

    desired {

```

## 20. Example: Database

```csl
resource Database version 1 {
    customer_id: uuid
    tenant: string
    display_name: string

    desired {
        engine: string oneof(postgres mysql mariadb)
        version: string
        storage: bytes range 1GiB+
        replicas: uint8 range 1 to 10 = 1

        backup_enabled: bool = false

        if desired.backup_enabled {
            backup_schedule: crontab
            backup_retention: uint16 range 1 to 365
        }
    }

    observed {
        phase: string oneof(pending provisioning running failed)
        endpoint: hostname optional
        port: port
        ready: bool = false
    }
}
```

## 21. Example: NetworkPolicy

```csl
resource NetworkPolicy version 1 {
    tenant: string
    network_id: uuid

    desired {
        default_action: string oneof(allow deny) = deny
        allowed_sources: cidr[0:256]
        allowed_destinations: cidr[0:256]
        allowed_ports: port[0:128]
    }

    observed {
        phase: string oneof(pending applying active failed)
        last_applied_at: timestamp optional
        error: string optional
    }
}
```

## 22. Future considerations

The following features are intentionally not finalized:

- Reusable enumeration declarations.
- Reusable validation constraints.
- Regular expression constraints.
- Explicit nullable types.
- Unique list and map-value constraints.
- Cross-field validation expressions.
- Field deprecation and removal annotations.
- Schema imports and modules.
- Explicit migration descriptions.
- Sensitive-field annotations.
- More comprehensive date/time and binary serialization rules.

These should be introduced only when supported by concrete use cases.
